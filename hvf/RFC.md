# RFC: macOS Hypervisor.framework support in rust-vmm (`hvf-bindings` and `hvf`)

Follow-up to rust-vmm/community#129.

## Summary

Add two crates to the rust-vmm monorepo, under `hvf/`:

- **`hvf-bindings`**: hand-written, dependency-free FFI bindings to the arm64
  Hypervisor.framework (HVF) API, verified against the macOS SDK headers.
  This is the equivalent of `kvm-bindings`.
- **`hvf`**: thin safe wrappers in the style of `kvm-ioctls`: `Hvf` (host
  probes, VM creation), `Vm`, `Vcpu`, `VcpuKicker`, `Gic`, and exit and
  syndrome decoding.

The same change makes the existing workspace build and test on
`aarch64-apple-darwin`. Linux-only crates (`kvm-ioctls`, `seccompiler`,
`event-manager`) compile to empty crates on macOS. `vmm-sys-util`,
`vm-memory` and `virtio-blk` get small portability fixes. Linux behaviour is
unchanged.

## Motivation

- **Demand.** Several Rust VMMs already run on Apple silicon through HVF:
  libkrun, ignition, hvi-vmm. Each carries its own bindings, and they differ
  in licence and quality. Cloud Hypervisor's HVF port attempt (#8451) stalled
  partly because no shared building block exists.
- **No maintained candidate.** The crates proposed in #129 (`hv` and
  `hv-sys`) have been dormant since 2024 and do not follow rust-vmm
  conventions.
- **Reuse.** rust-vmm's other crates (vm-memory, vm-device, linux-loader,
  vm-fdt, virtio) already work on macOS with small fixes. An HVF crate pair
  lets a VMM swap only the hypervisor layer.

## Design

### `hvf-bindings`

- **Hand-written, no bindgen.** The bindings carry the rust-vmm dual licence,
  Apache-2.0 OR BSD-3-Clause. Nothing is copied from GPL (QEMU) or
  Apache-2.0-only (libkrun) sources.
- **SDK names.** Names match the SDK exactly. `OS_ENUM` types become integer
  aliases with constants, not Rust enums, because Apple adds values.
- **Two `macro_rules!`.** `hv_consts!` and `hv_fns!` mirror `OS_ENUM` and
  `API_AVAILABLE`. They record each item in tables that a test checks
  against the SDK.
- **Linking.** Only macOS 11.0 functions are hard-linked. Newer functions
  (12.1 to 27.0) are resolved with `dlsym` into a `DynApi` table, so one
  binary runs on every release and Cargo needs no version features.
  Hard-linked declarations are available in a `direct` module for users who
  accept a newer minimum OS.
- **SIMD setter.** `hv_vcpu_set_simd_fp_reg` takes a 128-bit vector by
  value, which stable Rust cannot declare. A two-instruction naked
  tail-call trampoline handles it. This needs Rust 1.88, so the MSRV of the
  hvf crates is 1.88.
- **SDK verification.** `tests/sdk_check.rs` generates C from the tables and
  compiles it with `xcrun clang -Werror` against the installed SDK. It
  covers values, layouts, exact function prototypes and availability, and
  fails on any header item that is not bound. No Python and no build script
  are involved.

### `hvf`

- **Thin, no policy.** Like `kvm-ioctls`, the crate has no memory layout, boot
  protocol, PSCI, interrupt routing or device models.
- **Error handling.** The crate keeps only what turns HVF's opaque errors into
  checked ones:
  - granule and IPA-range checks on `map`, `unmap` and `protect`;
  - GIC layout validation;
  - `GicAfterVcpu` and `GicExists` ordering errors;
  - `Error::Unavailable { api, since }` for functions missing on the running
    release.
- **Soundness model.**
  - `Vcpu` is `!Send` and `!Sync`, because HVF vCPU calls are owner-thread
    only. This also guarantees `hv_vcpu_destroy` runs on the owning thread.
  - `Vm` and `Gic` are `Send` and `Sync`, since VM-level calls work from any
    thread.
  - `VcpuKicker` holds a shared `alive` lock across `hv_vcpus_exit` and
    `hv_vcpu_destroy`, so a stale kicker can never cancel a new vCPU that
    reuses the id.
  - `Vm::map` is `unsafe` with a contract like `KVM_SET_USER_MEMORY_REGION`.
    `unmap` is safe, because stage-2 invalidation is synchronous.
- **One VM per process.** HVF allows one VM per process. A three-state slot
  (free, live, zombie) makes `create_vm` return `VmExists` instead of
  undefined behaviour, and recovers when a destroy has to be retried.
- **vm-memory.** The optional `vm-memory` feature adds
  `Vm::map_guest_memory` for any `GuestMemoryBackend`. It validates every
  region first and rolls back on failure.
- **Portable parts.** Errors, register ids, exit decoding, MMIO arithmetic
  and alignment checks compile and are tested on every target, including
  Linux CI.

## Testing and CI

The biggest objection to HVF support so far has been "how is this tested
regularly?". The proposal:

1. **Linux Buildkite (unchanged pipeline).** The crates' `.platform` lists
   `x86_64` and `aarch64`. The existing autogenerated pipeline builds,
   tests, lints and measures coverage for the portable code. Coverage scores
   are in `coverage_config_*.json`.
2. **GitHub Actions on `macos-15` (arm64).** This job checks formatting,
   runs `cargo check`, clippy (`-D warnings -D
   clippy::undocumented_unsafe_blocks`) and `cargo test --workspace`, runs
   the SDK check, and builds the docs with `-D warnings`. Hosted runners
   have no nested virtualization, so HVF tests print `SKIP` there.
3. **Self-hosted Apple silicon Buildkite agents
   (`.buildkite/pipeline.macos.yml`).** These run the real HVF tests with
   `HVF_REQUIRE=1`, in debug and release builds, along with the example and
   the SDK check. The tests cover the VM lifecycle, memory, MMIO exits,
   threading and kicks, SIMD, registers, IRQ lines, the virtual timer and
   the in-kernel GIC. **We are asking whether rust-vmm can host such an
   agent, or accept one donated by the maintainers.** Until one exists,
   maintainers run this pipeline locally before each release, as the README
   documents.

Test binaries are ad-hoc signed with the `com.apple.security.hypervisor`
entitlement by a cargo runner (`hvf/scripts/codesign-run.sh`, configured in
`.cargo/config.toml`). This applies to `cargo test`, `cargo run` and
doctests.

## Alternatives considered

- **Adopt `hv`/`hv-sys` or `applevisor`.** `hv` is dormant. `applevisor` is
  maintained but follows a different API shape: it gates macOS versions with
  Cargo features, which hard-links symbols. Neither has rust-vmm's licence
  or review history.
- **bindgen at build time.** This would need libclang on every build and
  produce Rust enums for `OS_ENUM`s. Checked-in bindgen output would be
  possible, but the SDK check gives the same guarantee with readable
  sources.
- **One crate instead of two.** Splitting the crates matches `kvm-bindings`
  and `kvm-ioctls`, and lets VMMs with their own wrappers use only the
  bindings.

## Open questions

1. **Crate names.** Are `hvf-bindings` and `hvf` acceptable? Both are
   unclaimed on crates.io. `hvf-ioctls` was rejected as misleading, because
   HVF has no ioctls.
2. **Hosting.** Monorepo (`hvf/`, as here) or a separate repository?
3. **CI hardware.** Can rust-vmm provide a self-hosted macOS arm64 agent?
4. **Minimum OS.** The crates run on macOS 11.0 and later and report missing
   functions at run time. Should we instead document macOS 15+, where the
   in-kernel GIC exists, as the supported floor?
5. **MSRV 1.88** for the hvf crates, versus 1.85 for kvm-*. This is driven
   by naked functions.
6. **Follow-ups**, each as a separate PR: a kqueue backend for
   `event-manager`; `F_PUNCHHOLE` support in `vmm-sys-util`, so that
   virtio-blk's stdio backend works on macOS; SME accessors; and a
   `boot_linux` example.

## Maintainers

The proposers volunteer as code owners for `/hvf/`, together with existing
rust-vmm maintainers willing to review.
